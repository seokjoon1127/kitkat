# F3. 모션 블러 (고해성사 #5)

## 무엇을 잘못했나

실측 결과(1080×1920 1초): 최고 품질 `minterpolate=fps=240:mi_mode=mci + tmix=8` 이 **77초**.
나는 이걸 두고 **「30초 광고면 38분이라 실용 불가」** 라고 쓰고 `tmix`(0.8초)를 기본으로 밀었다.

**kitkat 은 에이전트가 돌리는 도구다.** 밤새 렌더 걸어두는 게 정상인 물건에서 38분이 왜 불가인가.
**사용자가 정할 문제를 내가 정하고, 싼 방법을 기본값으로 만들었다.**

## 세 가지 다른 문제다 — 하나로 뭉뚱그리면 안 된다

| | 무엇 | 지금 | 해법 |
|---|---|---|---|
| **A** | **소스 영상 속 피사체**가 안 흐림 (AI 영상이 「CG 같다」는 정체) | 없음 | ffmpeg 파생 (M2) |
| **B** | **트랜스폼 애니메이션**(켄번스 줌·팬·글자 이동)이 안 흐림 | 없음 | Remotion 합성 단계 |
| **C** | **전환**(휩팬·줌)에 블러가 없어 미끄러짐 | 없음 | SVG 방향성 블러 |

## A. 소스 영상 모션 블러 — ffmpeg 파생

### 실측 (1080×1920, 1초)
| 방법 | 시간 | 화질 |
|---|---|---|
| `minterpolate=fps=240:mi_mode=mci:mc_mode=aobmc` + `tmix=8` | **77초** | 매끈 (진짜 셔터) |
| `minterpolate=fps=120` + `tmix=4` | **36초** | 거의 같음 |
| `minterpolate=mi_mode=blend` + `tmix=8` | 1.9초 | 계단 보임 |
| `tmix=frames=3` | **0.8초** | 빠른 움직임에선 계단, 느린 움직임에선 거의 같음 |

**현실적 움직임(초당 250px)에서는 77초짜리와 0.8초짜리가 육안으로 거의 구분 안 됐다**(계단 2단).
**하지만 그게 「빠른 게 기본이어야 한다」는 뜻은 아니다.**

### 설계 — 셔터 각도로 표현한다
사용자에게 「프레임 몇 장 섞기」가 아니라 **영화 용어**로 준다:
```ts
motionBlur?: {
  shutterAngle: number;          // 0~360. 180 = 표준 영화, 360 = 최대 번짐
  quality: 'fast' | 'precise';   // 기본 'precise'  ← 기본값을 좋은 쪽으로
};
```
- `precise` = `minterpolate=fps=<fps×8>:mi_mode=mci:mc_mode=aobmc` → `tmix=frames=<8×각도/360>` → `fps=<fps>`
- `fast` = `tmix=frames=<round(3×각도/180)>` (보간 없음)
- **기본값은 `precise`.** 느린 건 진행률로 보여준다. 「빠름」은 사용자가 고르는 것이다.

### 예상 시간을 미리 알려준다
잡 등록 시 **소스 길이 × 실측 계수**로 예상 시간을 계산해 응답에 담는다
(`precise` ≈ 77초/초, `fast` ≈ 0.8초/초 — 첫 실행 때 실측해 보정).
UI 는 「약 38분 걸립니다. 계속할까요?」를 **묻고** 진행한다. 몰래 느린 걸 돌리지도, 몰래 빠른 걸로
바꾸지도 않는다.

## B. 트랜스폼 모션 블러 — Remotion 합성

### `@remotion/motion-blur` 는 A 를 못 한다 (확인 필요)
원본 소스 분석 결과 `<CameraMotionBlur>` 는 `<Freeze>` 로 서브프레임 N장을 그려 합산한다.
30fps 컴포지션 + 30fps 소스면 **샘플 10개가 전부 같은 소스 프레임**으로 떨어져
**비디오 속 피사체는 안 흐려진다.** 흐려지는 건 `useCurrentFrame()` 으로 계산되는
pan/zoom/rotation 뿐 — **즉 정확히 B 용이다.**

**⚠️ 이건 소스 코드 추론이다. F17 에서 실제 렌더로 확인한다.**

### 두 가지 길, 둘 다 만든다
**(B-1) 자체 구현 — 의존성 0, 권장**
kitkat 은 `computeVisualLayout(clip, asset, w, h, tMs)` 로 **임의 시각의 레이아웃을 계산할 수 있다.**
→ 한 프레임을 그릴 때 `tMs` 를 셔터 구간 안에서 N등분해 **레이아웃 N개를 계산하고
N장을 겹쳐 그린다**(`mixBlendMode:'plus-lighter'` + `opacity 1/N`).
`@remotion/motion-blur` 가 하는 일과 같지만 **버전 충돌이 없고**, 비디오 프레임은 한 번만 가져오므로
(같은 `tMs` 의 소스 프레임) **프레임 추출이 N배가 되지 않는다.**

**(B-2) `@remotion/motion-blur` 도입**
쓰려면 remotion 관련 패키지를 **전부 4.0.520 으로 같이 올려야 한다**
(`@remotion/motion-blur@4.0.520` 이 `remotion: '4.0.520'` 을 정확히 핀한다 — peer 아님).
→ **버전 일괄 상향은 별도 태스크로 분리**하고, B-1 을 먼저 만든다.

### 스키마
```ts
// ClipBase 에 추가
transformBlur?: { shutterAngle: number; samples: number };   // samples 4~32, 기본 12
```
**어떤 클립에든 걸린다** — 비디오·이미지·텍스트 전부. 글자가 날아 들어올 때 블러가 걸리는 게
「비싸 보이는」 이유다.

## C. 전환 방향성 블러 — SVG

`stdDeviation` 은 X/Y 를 따로 받는다. **한쪽이 0이면 그 방향으로만 번진다**(MDN 확인).
```
<feGaussianBlur stdDeviation="20 0"/>   ← 가로로만
```
각도는 **엘리먼트를 `rotate(θ)` 로 감싸고 안쪽을 `rotate(-θ)` 로 되돌린다** —
CSS filter 는 내용에 먼저 적용되고 그 결과에 transform 이 걸리므로 성립한다.

### 어디에
`packages/renderer/src/composition/svg-filters.tsx` 에 `dirBlur` 스테이지 추가.
`transitions.tsx` 의 전환 정의에 **블러 강도 곡선**을 붙인다 — 전환 중앙에서 최대, 양끝에서 0.
- `slideLeft/Right` → 가로 블러
- `slideUp/Down` → 세로 블러
- `zoomIn/Out` → **방사형이 필요한데 SVG 로는 안 된다.** `@remotion/effects` 의 `zoomBlur`
  (WebGL2)가 있지만 S5 의 `chromiumOptions` 가 선행이다. **당분간은 등방 블러로 근사하고
  「근사」라고 문서에 적는다.** ← 이건 포기가 아니라 순서 문제다. F15 에서 다시 온다.
- `whipPan` 신규 추가 — 강한 방향성 블러 + 빠른 슬라이드. **광고 전환의 기본기다.**

**렌더 시간이 안 늘어난다** — 프레임을 더 뽑지 않는다.

## 검증

**A**: 합성 이동 물체로 `shutterAngle` 0/90/180/360 의 번짐 길이를 픽셀로 측정 —
각도에 비례해 늘어나는지. `precise` vs `fast` 를 현실적 속도(250px/s)와 극단(1600px/s) 양쪽에서 비교.
**예상 시간 계산이 실제와 ±20% 안에 드는지도 검증한다.**

**B**: 켄번스 줌 클립을 `transformBlur` 있음/없음으로 렌더해 정지 프레임의 엣지 선명도
(라플라시안 분산)를 비교. 값이 낮아져야(=흐려져야) 한다.

**C**: 각 전환의 중앙 프레임에서 블러 방향이 이동 방향과 일치하는지 —
가로 블러면 세로 엣지만 뭉개져야 한다. 방향별 그래디언트 크기로 측정.

## 하지 않을 것
- **기본값을 `fast` 로 두지 않는다.** 좋은 쪽이 기본이고, 느린 건 미리 알려준다.
- 「실용 불가」 같은 판정을 내리지 않는다. 시간을 적고 사용자가 고른다.
