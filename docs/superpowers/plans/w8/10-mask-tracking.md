# F10. 마스크 모션 트래킹

## 무엇을 하나

**마스크가 화면 속 대상을 스스로 따라가게 한다.** 지금 `Mask` 는 고정 사각형이라,
움직이는 사람 얼굴을 가리려면 **프레임마다 손으로 위치를 찍어야 한다** — 30초면 900번이다.
영상에서 대상을 자동 추적해 프레임별 위치·크기를 뽑고, 그 결과를
`mask.x` / `mask.y` / `mask.w` / `mask.h` **키프레임으로 넣는다.**

「얼굴 모자이크」·「간판 가리기」·「사람만 밝게」·「제품에만 글로우」가 이걸로 된다.

**S1(키프레임 경로 확장)이 선행 조건이다.** `Keyframe.prop` 이 6종 열거형인 동안에는
마스크에 키프레임을 걸 방법이 없다 — 추적을 아무리 잘해도 넣을 자리가 없다.
그래서 실행 순서가 **S1 → F13 → F10** 이다.

## 무엇으로 추적하나 — `TrackerVit`

**OpenCV 의 `TrackerVit` 을 쓴다.** 후보를 전부 비교한 결과다.

| | **TrackerVit (채택)** | TrackerNano | CSRT | ffmpeg |
|---|---|---|---|---|
| 패키지 | **`opencv-python-headless` 기본에 포함** (contrib 불필요) | 기본 포함 | **contrib 필요 (53.8MB 추가)** | 이미 있음 |
| 휠 크기 | 43.8MB | 43.8MB | +53.8MB | — |
| 모델 | `object_tracking_vittrack_2023sep.onnx` **0.71MB**, **Apache-2.0** | 별도 2개 | 없음 | — |
| 속도 | **공식 벤치 4.01ms/프레임** (1280×720, Intel 12700K) ≈ 실시간의 8배 | 비슷 | **25fps = ViT 의 1/10** | — |
| **추적 실패를 알 수 있나** | **예 — 점수가 떨어진다** | **아니오** | 대략 | — |
| 물체 위치를 주나 | 예 | 예 | 예 | **아니오** |

### `TrackerNano` 가 아닌 이유 — 이게 결정적이다

OpenCV 공식 README 가 밝히고 있다: **Nano 는 어떤 상황에서도 0.9 점수만 돌려준다.**
대상을 완전히 놓쳐 엉뚱한 곳을 따라가고 있어도 0.9다.

**편집기는 「여기서부터 놓쳤습니다」를 보여줘야 한다.** 실패를 못 알려주는 추적기는
900개의 틀린 키프레임을 조용히 만들어 놓고, 사용자는 렌더를 다 돌린 뒤에야 안다.
0.4ms 더 빠른 것보다 이게 훨씬 중요하다.

### CSRT 가 아닌 이유

`opencv-contrib-python` **53.8MB 를 추가로** 받아야 하고, **25fps** 다 —
30초 1080p30 이면 900프레임 ÷ 25 = **36초**. ViT 는 같은 조건에서 3.6초.
정확도가 ViT 보다 확실히 낫다는 근거도 없다.

### ffmpeg 으로는 안 된다 (조사에서 직접 확인)

- **`vidstabdetect` 의 `.trf`** — 바이너리를 열어 확인한 결과 **프레임 전체의 카메라 이동**이지
  물체 위치가 아니다. 손떨림 보정용이다.
- **`mestimate`** — 모션 벡터를 내보낼 방법이 없다.

### CoTracker3 · SAM2 는 과하다

CPU 로 실용 속도가 안 나온다. **venv 에 torch 2.13.0 이 이미 있다는 사실은 선택을 바꾸지
않는다** — OpenCV 트래커는 torch 가 아니라 자체 DNN 모듈 + ONNX 를 쓴다.

## 붙이는 자리와 입출력 계약

### 파일

| 파일 | 역할 | 본뜰 것 |
|---|---|---|
| `packages/ai/python/track.py` | 추적 (신규) | `packages/ai/python/transcribe.py` |
| `packages/ai/src/track.ts` | 노드 래퍼 (신규) | `packages/ai/src/index.ts:93-121`, `demucs.ts` |
| `packages/server/src/routes/media-ops.ts` | HTTP + 잡 | 같은 파일의 `separate`(48줄) |

**whisper · demucs 와 정확히 같은 자리·같은 규약**이다:
`VENV_PYTHON` 으로 실행 → stdout 에 JSON → 모듈이 없으면 **exit 3** → 노드가
`AiUnavailableError` → 서버가 **HTTP 501** + 설치 안내.

### 명령줄

```
python track.py <media 절대경로>
  --box  <x> <y> <w> <h>        # 시작 사각형, «소스 픽셀» 단위
  --anchor-ms <int>             # 시작 프레임 (소스 파일 기준 ms)
  --from-ms <int> --to-ms <int> # 추적 범위 (소스 파일 기준)
  --direction forward|backward|both
  --model <onnx 경로>
```

### stdout (JSON)

```json
{
  "sourceFps": 29.97,
  "width": 1080, "height": 1920,
  "frames": [
    { "ms": 0,  "x": 412.0, "y": 233.5, "w": 180.0, "h": 240.0, "score": 0.94, "ok": true },
    { "ms": 33, "x": 415.2, "y": 236.1, "w": 181.3, "h": 239.0, "score": 0.91, "ok": true },
    { "ms": 66, "x": 0,     "y": 0,     "w": 0,     "h": 0,     "score": 0.11, "ok": false }
  ]
}
```

- **좌표는 소스 파일의 픽셀 그대로.** 정규화·크롭 보정은 **노드가 한다**(아래 §좌표 변환).
  파이썬이 kitkat 의 레이아웃 규칙을 알 필요가 없다.
- `ms` 는 **소스 파일 기준 정수 ms**.
- `ok:false` 인 프레임도 **빠뜨리지 않고 넣는다.** 「어디서 놓쳤는지」가 결과의 일부다.

### 진행률

기존 두 스크립트는 진행률을 안 낸다(끝날 때 JSON 한 덩어리). 추적은 수십 초가 걸릴 수 있으므로
**stderr 한 줄 규약**을 새로 둔다:

```
PROGRESS 0.42
```

`execa` 의 stderr 스트림에서 이 줄만 골라 `report(p)` 로 넘긴다. 다른 stderr 출력은
지금처럼 오류 메시지로 모은다.

### 서버

```
POST /api/projects/:id/clips/:clipId/track
  { box: {x,y,w,h},        // 클립 상자 기준 정규화 0..1 (= 지금 mask 와 같은 단위)
    anchorMs: number,      // 클립 시작 기준 ms
    range?: { start, end },// 클립 기준 ms. 기본 클립 전체
    direction?: 'forward'|'backward'|'both',   // 기본 'both'
```

`track: 30 * MIN`.

## 좌표 변환 — 가장 틀리기 쉬운 곳

파이썬은 **소스 픽셀**을 주고, `Mask` 는 **클립 상자 대비 0..1** 을 받는다.
그 사이에 **contain-fit** 과 **크롭**이 있다.

`computeVisualLayout`(`layout/index.ts:76-86`)에서 그대로 유도된다:

```
fit  = min(canvasW/aw, canvasH/ah)       aw,ah = 소스 크기
fitW = aw·fit,  fitH = ah·fit
boxW = fitW·crop.w,  boxH = fitH·crop.h
inner.left = −crop.x·fitW

소스px sx  →  상자로컬px = sx·fit − crop.x·fitW
           →  정규화 nx = (sx/aw − crop.x) / crop.w
```

```
nx = (sx/aw − crop.x) / crop.w        ny = (sy/ah − crop.y) / crop.h
nw = (sw/aw) / crop.w                 nh = (sh/ah) / crop.h
crop 이 없으면 crop = {x:0,y:0,w:1,h:1}
```

**여기에 캔버스 크기·`scale`·`rotation` 이 들어가지 않는 것이 핵심이다** —
그것들은 상자 «전체»에 걸리고 마스크는 상자 «안»에 살기 때문이다.
그래서 클립을 나중에 확대하거나 회전해도 **추적 결과가 그대로 유효하다.**

이 변환은 `packages/renderer/src/layout/index.ts` 에 **정변환과 나란히** 둔다
(`maskNormFromSourcePx` / `sourcePxFromMaskNorm`). UI 도 서버도 이 함수만 부른다.

### 시간축 변환 — `speed` · `reversed` · `speedRamp`

파이썬은 **소스 ms** 로 답하고 키프레임은 **클립 ms** 를 쓴다.

| 클립 | 소스 ms → 클립 ms |
|---|---|
| 보통 | `(srcMs − clip.in) / clip.speed` |
| `reversed` | `(clip.out − srcMs) / clip.speed` |
| `speedRamp` | `rampSegments(clip)`(`schema/derive.ts`)가 주는 **등속 구간별**로 역산 |
| `freeze` | 추적할 것이 없다 — **거부**하고 이유를 말한다 |
| `loop` | 소스 구간이 반복된다 — 한 바퀴만 추적해 **반복 복제** |

`rampSegments` 는 이미 「소스 구간 진행도 ↔ 시간」을 계산하고 있으므로 역함수는
구간 이진탐색 + 선형보간 **약 20줄**이다. **speedRamp 를 「지원 안 함」으로 두지 않는다** —
속도 램프가 걸린 컷이야말로 손으로 키프레임을 찍기 제일 괴로운 컷이다.

## 키프레임 폭발 — 반드시 같이 해결한다

30초 30fps = **900프레임 × 4경로 = 3,600 키프레임**. 그냥 넣으면 두 가지가 터진다.

1. **문서 크기** — 키프레임 1개가 JSON 약 60바이트 → 클립 하나에 **약 216KB**.
   컷 10개면 2MB 짜리 프로젝트 파일이 된다.
2. **보간 비용** — 지금 `interpolateKeyframes` 는 호출마다 `filter().sort()` 를 돌린다
   (`renderer/composition/keyframes.ts:47`). 3,600개 × 4경로 × 900프레임 =
   **약 1,300만 번의 비교**. → **F13 의 경로별 묶음 캐시(WeakMap)가 필수 선행이다.**

### 키프레임 간소화 — RDP

**Ramer–Douglas–Peucker** 로 궤적을 단순화한다. 「원래 곡선에서 `tolerancePx` 이상 벗어나지
않는 최소 점 집합」을 고르는 표준 알고리즘이고 약 30줄이다.

**채널을 따로 줄이면 안 된다.** x 와 y 가 서로 다른 시각에 키프레임을 가지면 그 사이에서
사각형이 미묘하게 흔들린다. → **(x,y) 를 2차원 궤적으로, (w,h) 를 2차원 궤적으로** 각각 RDP 한 뒤
**남은 시각의 합집합**에 네 값을 모두 심는다.

```
tolerancePx 기본 0.5 (1080 기준 정규화로 약 0.00046)
```

**예상 감소율 80% 이상 — 확인 필요.** 매끄러운 팬에서는 900 → 40~120 점이 될 것으로 보지만
**실제로 재지 않았다.** §검증 5에서 실측해 숫자를 문서에 적는다.
UI 에는 슬라이더로 노출한다(**정밀 ↔ 가벼움**), 기본 0.5px.

**`ok:false` 구간의 키프레임은 만들지 않는다.** 실패 구간 앞뒤의 성공 키프레임 사이를
그냥 보간하면 마스크가 스르르 지나가 버려서 **실패한 줄 모른다.** 실패 구간은
**비워 두고 UI 가 빨갛게 표시한다.**

## 실패를 어떻게 보여주고 어떻게 고치나

### 감지

`tracker.getTrackingScore()` 를 프레임마다 읽는다.

```
score < FAIL_THRESHOLD  →  ok:false
FAIL_THRESHOLD 기본 0.30  ← 확인 필요
```

**0.30 은 추정값이다.** 실제로 정할 방법: 아래 §검증 4에서 **일부러 실패시킨 영상**
(대상이 화면 밖으로 나감 / 완전히 가려짐 / 조명 급변)의 점수 분포와 성공 구간의 분포를
히스토그램으로 찍어, **두 분포가 갈리는 지점**을 임계로 잡는다. 값을 코드에 박기 전에 잰다.

연속 실패 3프레임 미만은 **일시적 흔들림**으로 보고 앞뒤를 이어 준다(깜빡임 방지).

### UI — 타임라인에 띠 하나

클립 위에 **추적 결과 띠**를 그린다.

```
클립 ▐████████████░░░░████████▌
      추적됨      실패  추적됨
     └ 초록 ─┘  └빨강┘ └ 초록 ─┘
```

- 띠를 클릭하면 그 시각으로 재생헤드가 간다
- 빨간 구간 위에 **「12번째 프레임부터 대상을 놓쳤습니다」** 툴팁
- 초록 구간의 진하기 = 점수 (0.3~1.0 을 밝기로) — 「위태로운 구간」이 보인다

### 고치는 법 — 두 가지

**(a) 다시 잡기 (권장)**
1. 실패 구간의 아무 프레임으로 이동
2. 마스크를 손으로 대상 위에 맞춘다 (마스크 상자를 드래그)
3. **[여기서 다시 추적]** — 그 프레임을 새 기준으로 트래커를 초기화하고
   **그 시점 이후만** 다시 돌린다. 앞쪽 키프레임은 보존한다.

**(b) 손 키프레임**
실패 구간 안에서 마스크를 옮기면 F13 의 「◆ 키프레임 추가」가 그대로 동작한다.
자동 결과와 손 결과가 **같은 종류의 키프레임**이라 섞어 쓸 수 있다 — 이게 결과를
키프레임으로 넣는 설계의 이점이다.

### 되돌리기

추적 결과는 **`setKeyframes` 명령 한 건**으로 들어간다 → 문서 되돌리기 1회로 통째로 취소된다.
추적 전 키프레임은 명령 로그에 남는다.

## 검증 — 숫자로 낸다

**1. 이 컴퓨터의 실측 속도 (조사에서 «확신 못 하는 것»으로 남긴 항목)**
공식 4.01ms 는 **1280×720, Intel 12700K** 이고 이 컴퓨터에서 재지 않았다.
- 실제 1080×1920 클립 300프레임을 돌려 **ms/프레임**을 낸다 (디코딩 시간과 분리해서)
- 30초 30fps(900프레임) 환산 **총 시간**을 적는다
- **비교 대상**: 디코딩만 했을 때(PyAV 단독) — 추적이 실제로 얼마를 더 쓰는지
- **합격 기준 없음. 숫자를 적는 것이 목표다.** 느리면 느리다고 적고 선택지로 남긴다.

**2. 정확도 — 정답을 아는 영상으로**
합성 영상을 만든다: 검은 배경 위 100×100 흰 사각형이 **알려진 경로**로 움직인다
(사인파 왕복 5초, 30fps).
- **중심 좌표 오차**: 평균 ≤ 3px, 최대 ≤ 10px
- **IoU**(겹침 비율): 프레임 평균 ≥ 0.85

**3. 스케일 변화 추종 (조사의 «확인 못 함» 항목)**
같은 합성 영상에서 사각형이 **1.0배 → 2.0배**로 5초에 걸쳐 커진다.
- **폭 오차**: `|추적 w − 실제 w| / 실제 w` 평균 **≤ 10%**, 최대 **≤ 20%**
- 못 맞추면 **그 수치를 그대로 적고**, UI 에 「크기 변화가 큰 대상은 중간에 다시 잡아 주세요」를
  표시한다. **못 하는 것을 안 하는 것처럼 적지 않는다.**

**4. 실패 감지가 실제로 되는지**
세 가지 실패 영상을 만든다: ① 대상이 화면 밖으로 나감 ② 3초간 완전히 가려짐
③ 조명이 갑자기 4배 밝아짐
- 각 구간에서 **점수가 실제로 떨어지는지** 프레임별 점수를 그래프로 뽑는다
- 성공 구간 점수 분포와 실패 구간 점수 분포를 **히스토그램으로 겹쳐** 임계값을 정한다
- **거짓 실패**(잘 따라가는데 낮은 점수) 비율 ≤ 5%, **놓친 실패**(못 따라가는데 높은 점수) 0건
- **놓친 실패가 1건이라도 나오면** 임계를 올리고 다시 잰다. 이게 Nano 를 버린 이유 그 자체다.

**5. 키프레임 간소화 실측**
실제 영상 3종(느린 팬 / 사람 걷기 / 빠른 손동작)에서
| tolerancePx | 남은 키프레임 수 | 원본 대비 최대 편차(px) |
|---|---|---|
| 0.25 / 0.5 / 1.0 / 2.0 | 실측 | 실측 |
을 표로 낸다. **기본값 0.5 가 타당한지 이 표로 판단한다.**

**6. 좌표 변환 (사람이 제일 많이 틀리는 곳)**
소스 해상도 × 캔버스 비율 × 크롭의 조합 12가지에서, **소스에서 알려진 위치**의 물체를
추적해 마스크가 **화면에서 그 물체 위에 오는지** 렌더 픽셀로 확인 — **±3px**.
- 세로 영상(1080×1920)에 가로 소스(1920×1080) → 위아래 여백 있는 경우
- 크롭 `{x:0.25,y:0,w:0.5,h:1}` 이 걸린 경우
- `reversed` 클립
- `speed: 2` 클립
- `speedRamp` 가 걸린 클립

**7. 성능 회귀 (F13 캐시가 실제로 필요한지)**
간소화 **없이** 3,600 키프레임을 넣은 클립의 30초 렌더 시간을
(a) 묶음 캐시 있음 (b) 없음 으로 각각 재서 표에 적는다. 캐시가 왜 필수인지의 근거다.

**8. 끝에서 끝까지**
실제 세로 영상에서 사람 얼굴을 잡아 모자이크(`blur` 효과 + path 마스크)를 걸고 30초를 렌더한다.
**모든 프레임에서 얼굴이 가려져 있는지 사람이 눈으로 확인**하고, 안 가려진 프레임 수를 센다.
**0이 아니면 그 수를 적는다.**

## 하지 않을 것

- **`TrackerNano` 로 바꾸지 않는다.** 조금 더 빠르지만 실패를 알 수 없다.
- **실패 구간을 키프레임으로 메우지 않는다.** 앞뒤를 이어 보간하면 마스크가 대상을 지나쳐
  가면서도 「추적된 것처럼」 보인다. 비워 두고 빨갛게 표시한다.
- **속도를 이유로 기본 `stride` 를 2 이상으로 두지 않는다.** 기본은 **매 프레임**이다.
  건너뛰기는 사용자가 명시적으로 켜는 옵션이다.
- **`speedRamp`·`reversed` 클립을 「지원 안 함」으로 두지 않는다.** 시간축 역함수를 만든다.
  `rampSegments` 가 이미 절반을 해 준다.
- **간소화 없이 3,600 키프레임을 그냥 넣지 않는다.** 그리고 **간소화를 이유로 정확도를
  기본값에서 깎지 않는다** — 0.5px 는 1080 화면에서 보이지 않는 크기다.
- **`opencv-contrib-python` 을 「혹시 몰라서」 함께 깔지 않는다.** 53.8MB 를 쓰는데 쓸 일이 없다.
- **numpy 를 낮춰서 opencv 를 맞추지 않는다.** demucs·faster-whisper 가 같은 venv 를 쓴다.
- **공식 벤치 4.01ms 를 「이 컴퓨터에서도 그럴 것」으로 적지 않는다.** 재고 적는다.
