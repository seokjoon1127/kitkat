# F15. 프리뷰 v2 미지원 8종 구현 (고해성사 #8)

## 무엇을 잘못했나

빠른 미리보기(WebGL)가 못 그리는 것 8가지를 **배지로 「못 그립니다」 표시하고 완료 처리**했다.

> 아예 못 그린다(배지 뜸) — 마스크, 크로마키, sharpen, glow, chromaShift, grain, scanlines,
> lightLeak, glitch 전환의 찢김 덮개

크로마키는 나중에 W6 에서 고쳤다(사용자가 크로마키 자체를 지적해서). **나머지는 그대로다.**
배지는 「정직」이지 「완료」가 아니다. 전부 WebGL 셰이더로 구현 가능한 것들이다.

## 지금 못 그리는 것과 각각의 해법

`packages/ui/src/preview/gl.ts` 는 이미 WebGL2 프래그먼트 셰이더(672줄)를 갖고 있고,
색 테이블 룩업·색행렬·블렌드 11종·전환 15종을 정확히 그린다. **여기에 8개를 더하는 일이다.**

| # | 못 그리는 것 | 왜 | 해법 |
|---|---|---|---|
| 1 | **마스크** (rect/circle/linear + feather) | CSS mask-image 를 셰이더로 안 옮김 | 셰이더에서 거리 함수로 직접 계산 — **가장 쉽다** |
| 2 | **sharpen** | 이웃 픽셀이 필요(3×3 컨볼루션) | 텍스처 오프셋 샘플링 9회 |
| 3 | **glow** | 블러 + 임계 + screen 합성 | **2패스** — 임계 추출 → 가우시안 블러(분리형) → 합성 |
| 4 | **chromaShift** | R/B 채널을 다른 위치에서 샘플 | 셰이더 3줄 (`texture(tex, uv±offset)`) |
| 5 | **grain** | 프레임마다 다른 노이즈 | 셰이더 해시 노이즈 + 프레임 seed |
| 6 | **scanlines** | 주기적 가로줄 | 셰이더 `fract(uv.y * lines)` |
| 7 | **lightLeak** | 대각 그라디언트 + screen | 셰이더 그라디언트 |
| 8 | **glitch 전환 덮개** | 찢김 슬라이스 + 색 분리 | 셰이더에서 y 구간별 uv 이동 |
| (9) | **blur 근사** | 지금 밉맵 LOD 로 근사 | 3번의 분리형 가우시안으로 **정확히** |

**4·5·6·7·8 은 셰이더 몇 줄이다.** 1·2 는 조금 더. 3(과 9)만 2패스 구조가 필요하다.

## 구조 변경 — 다중 패스

지금 `gl.ts` 는 **단일 패스**(텍스처 → 셰이더 → 캔버스)다. glow·정확한 blur 는
「중간 결과를 텍스처에 그리고 다시 읽는」 과정이 필요하다.

```ts
// packages/ui/src/preview/gl-passes.ts (신규)
/** 오프스크린 프레임버퍼 2장을 번갈아 쓰는 핑퐁 렌더링 */
export class PassChain {
  begin(w: number, h: number): void;
  run(program: WebGLProgram, uniforms: Uniforms): void;   // 결과가 다음 패스의 입력
  finish(target: WebGLFramebuffer | null): void;
}
```
- FBO 2장 + 텍스처 2장을 만들어 번갈아 쓴다.
- **가우시안 블러는 분리형**(가로 1패스 + 세로 1패스)으로 한다 — N² → 2N 샘플.
- 패스가 필요 없는 클립은 **지금처럼 단일 패스**로 간다(성능 회귀 방지).

## 렌더러와 갈리지 않게 하는 장치

**이게 이 태스크의 핵심 위험이다.** 같은 효과를 SVG 필터(렌더)와 GLSL(미리보기)로 두 번 구현하면
반드시 갈린다. W6 에서 색조정 커브 순서가 갈렸던 것과 같은 일이 8번 더 생길 수 있다.

**대책:**
1. **수치는 `@kitkat/renderer/layout` 에서만 나온다.** `computeVisualLayout` 이
   `svgFilters`/`effectFilters` 스테이지에 이미 파라미터를 담고 있다. GLSL 은 **그 값을 유니폼으로
   받기만** 한다. 셰이더 안에서 파라미터를 다시 계산하지 않는다.
2. **효과마다 대조 테스트를 만든다** — 같은 클립을 (a) 서버 렌더 (b) WebGL 미리보기로 뽑아
   **픽셀 차이의 평균·최대**를 잰다. 임계(예: 평균 채널당 3, 최대 12)를 넘으면 실패.
   **8개 전부에 대해 이 테스트를 만든다.**
3. 대조 테스트는 **헤드리스 Chrome 에서 실제로 셰이더를 컴파일해 픽셀을 읽는다.**
   W6 에서 이 방법으로 셰이더를 검증한 전례가 있다(커브 순서: 77 vs 93 으로 판별).

## 배지의 새 역할

8개를 구현하면 배지에 남는 것은:
- **근사인 것** — 색보정 순서(temperature/tint vs highlights/shadows 상대 순서)
- **아직 대기인 것** — F16 에서 「WebGL 필요」로 표시한 신규 효과들

배지가 「못 그림」에서 **「이만큼 다름」**으로 바뀐다. 대조 테스트의 실측 차이를 배지에 띄운다
(예: 「이 구간은 최종 렌더와 색이 최대 4 다릅니다」). **숫자가 있는 정직이 훨씬 쓸모 있다.**

## 검증

**정확도** — 8개 각각에 대해 서버 렌더 vs WebGL 픽셀 대조. 평균·최대 차이를 표로 보고.
**임계를 못 맞추는 것이 있으면 그 사실과 수치를 그대로 적는다.** 조용히 배지로 돌리지 않는다.

**성능** — 8개를 전부 켠 클립에서 재생 fps. 단일 패스 클립의 fps 가 **떨어지지 않는지**(회귀).

**셰이더 컴파일** — 헤드리스 Chrome 에서 실제 컴파일. **SwiftShader 와 실제 GPU 양쪽**에서
(이 컴퓨터의 GPU 사고 이력 때문에 SwiftShader 를 기본 검증 환경으로).

**메모리** — FBO 2장 추가로 늘어난 GPU 메모리. 1080×1920 RGBA 2장 = 약 16MB. 문제없어야 하지만 잰다.

## 하지 않을 것
- **배지를 「완료」로 치지 않는다.**
- 어려운 것(glow 2패스)을 빼고 쉬운 것만 하지 않는다. **8개 전부.**
