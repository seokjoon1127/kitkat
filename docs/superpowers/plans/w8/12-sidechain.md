# F12. 진짜 사이드체인 더킹 (고해성사 #7 — 보류 철회)

## 무엇을 잘못했나

W7 조사에서 진짜 사이드체인을 두 번 반려했고, **두 번 다 확인하지 않은 것을 근거로 했다.**

1. **「kitkat 구조에 안 맞는다」** — Remotion 이 렌더할 때 오디오를 어떻게 섞는지 확인하지 않고
   단정했다. 확인해 보니 `node_modules/@remotion/renderer/dist/` 에 `preprocess-audio-track.js` ·
   `merge-audio-track.js` · `combine-audio.js` · `mux-video-and-audio.js` 가 있고,
   **Remotion 은 오디오를 자체 ffmpeg 파이프라인으로 섞는다.** `preprocess-audio-track` 이 거는
   필터는 `volume` 하나뿐이고, `wav`·`mp3`·`aac` 가 유효 코덱이라 **오디오 전용 렌더가 된다.**
2. **「미리보기와 렌더가 달라져서 원칙이 깨진다」** — PRD 를 다시 읽지 않고 썼다.
   **P3 는 「결과물 무타협, 미리보기는 프록시」다.** 미리보기가 근사인 것은 **원칙 그 자체**이지
   위반이 아니다. 이미 미리보기는 배속 16 클램프·볼륨 1 클램프로 근사하고 있다.

**그리고 실제로 돌려서 증명했다.** `Track.muted` 를 번갈아 켜 스템 2장을 렌더하고
`sidechaincompress` 로 섞었다. 목소리가 3~7초에만 있는 10초 프로젝트:

```
0~2초  (목소리 없음)  음악만 -12.2dB → 최종 -12.2dB   손 안 댐
4~6초  (목소리 있음)  음악만 -12.1dB → 최종 -15.6dB   눌림
8~10초 (목소리 없음)  음악만 -12.1dB → 최종 -12.1dB   다시 열림
```

**비용 (1080×1920, 5초 실측):** 영상+오디오 22.24초 · 오디오 전용 12.71초 · 사이드체인 믹스 0.72초
→ 스템 2장 + 믹스 = `22.24 + 12.71×2 + 0.72` ≈ **48초. 지금의 2.2배.**

## 이 문서는 두 가지를 한다

| | 무엇 | 어디에 |
|---|---|---|
| **A** | **진짜 사이드체인** — 렌더 시 스템 2장 + `sidechaincompress` | 렌더 파이프라인 |
| **B** | **지금의 키프레임 더킹 개선** — 「클립 존재」 → **파형 포락선** | 엔진 + 파형 |

**둘 다 필요하다.** A 는 렌더 결과의 품질, B 는 미리보기의 정확도와 **A 를 끄고 쓸 때의 품질**이다.

**즉 지금 방식이 가짜가 아니다.** 문제는 방식이 아니라 **입력 해상도**였다.

# A. 진짜 사이드체인

## 스키마

```ts
// packages/schema/src/index.ts — Track 에 추가 (전부 optional, v1 문서 그대로 유효)
export type Track = {
  /* 기존 */
  duckedBy?: string;   // 이 트랙을 «누르는» 트리거 트랙 id (보통 나레이션 트랙)
  duck?: { amount: number; attackMs: number; releaseMs: number };
};
```
- **`amount` 는 0..1 배율로 통일한다** — 미리보기(키프레임)와 렌더(사이드체인)가 **같은 숫자**를
  써야 사용자가 혼란스럽지 않다. 컴프의 `threshold`/`ratio` 는 여기서 역산한다(아래).
  UI 는 dB 를 같이 표시한다: 「원래의 25% (−12dB)」.
- `attackMs`/`releaseMs` 는 `sidechaincompress` 의 `attack`/`release` 로 그대로 간다
  (범위 0.01..2000 / 0.01..9000 — 확인함). 지금 엔진의 0..5000 제한과 겹친다.
- **엔진 검증:** `duckedBy` 가 자기 자신이면 `BAD_DUCK`. `duckedBy` 를 따라가 **순환**이면 `BAD_DUCK`.
  트리거 트랙이 `muted` 면 `BAD_DUCK`(눌릴 일이 없다).

`Track` 이 바뀌므로 `TrackSchema`(zod)에도 같이 추가한다.

## 렌더 잡 4단계 — S5 의 `renderAudioStem` 을 쓴다

```
1) 트리거 스템 (wav)   renderAudioStem(doc, { soloTrackIds: [triggerTrackId] })
2) 눌릴 스템   (wav)   renderAudioStem(doc, { soloTrackIds: [duckedTrackId] })
3) 영상 + 나머지 트랙  renderProject(doc', ...)   ← doc' 은 위 두 트랙을 muted
4) 믹스 + 먹싱         ffmpeg 한 번
```

**스템을 먼저 하는 이유:** 3번이 제일 오래 걸리는데(22초/5초), 사용자가 트랙을 잘못 골라
**트리거 스템이 무음**이면 22초를 버린다. 1·2번이 끝난 시점에 트리거 스템의 라우드니스를 재서
**−70 LUFS 이하(사실상 무음)면 3번을 시작하기 전에 실패**시킨다.

**진행률 가중치** — 실측(12.71 / 12.71 / 22.24 / 0.72, 합 48.38)에서:
```
[1] 0.26   [2] 0.26   [3] 0.46   [4] 0.02
```
S5(c)가 요구한 「단계 가중치로 일반화」가 이것이다. `deriveMedia` 의 `done/passes` 와 같은 형태로
쓰되 가중치가 균등하지 않으므로 누적 배열을 쓴다.

## 4단계 필터그래프

입력: `[0]` = 3번의 영상 mp4(나머지 트랙 오디오 포함 가능) · `[1]` = 눌릴 스템 · `[2]` = 트리거 스템

```
[2:a]asplit=2[vdet][vout];
[1:a][vdet]sidechaincompress=level_sc=<G>:threshold=<T>:ratio=4:attack=<A>:release=<R>
                            :makeup=1:knee=6:detection=rms:link=average[mduck];
[mduck][vout][0:a]amix=inputs=3:duration=longest:normalize=0[out]
```
```
-map 0:v -map "[out]" -c:v copy -c:a aac -b:a 192k -ar 48000
```
- 영상은 **`-c:v copy`** — 재인코딩하지 않는다. 4단계가 0.72초인 이유다.
- **`normalize=0` 이 필수다.** `amix` 기본값은 입력 수로 나눠서 전체가 1/3 이 된다.
- 3번 영상에 오디오가 없으면 `inputs=2` 로 줄이고 `[0:a]` 를 뺀다.
- **`asplit` 이 필요한 이유:** ffmpeg 필터그래프에서 출력 패드는 한 곳에만 연결된다.
  트리거를 「감지용」과 「들리는 소리용」 두 곳에 쓰려면 반드시 쪼개야 한다.

## ⚠️ 실측 함정 — 나레이션이 조용하면 더킹이 아예 안 걸린다

**같은 인자인데 나레이션 녹음 레벨만 바꾸면 (W7 실측):**

| 목소리 진폭 | 더킹 깊이 |
|---|---|
| 0.10 | **−0.1 dB (사실상 안 눌림)** |
| 0.50 | −7.9 dB |
| 1.00 | −12.3 dB |

**사용자가 「12dB 더킹」을 골랐는데 0dB 가 된다.** 조용히. 이게 이 기능에서 도망갈 수 있는
제일 큰 구멍이다.

### 어떻게 막나 — 조사안을 고쳤다

W7 조사가 증명한 필터그래프는 이렇다:
```
[1:a]loudnorm=I=-16:TP=-1.5:LRA=11[v];   ← asplit «앞»에 loudnorm
[v]asplit=2[vsc][vout];
```
**이러면 들리는 나레이션까지 −16 LUFS 로 덮어쓴다.** 사용자가 나레이션 트랙 볼륨을 조절해 놨든,
F11 의 나레이션 체인이 −14 로 맞춰 놨든 **전부 무시된다.** 더킹을 켰다고 나레이션 크기가 바뀌면 안 된다.

**대신 `sidechaincompress` 의 `level_sc`(사이드체인 입력 게인, 범위 0.015625..64 — 확인함)를 쓴다.**
1·2단계가 끝난 뒤 **트리거 스템의 통합 라우드니스를 한 번 재고**(60초에 0.2초):
```
G = 10^((-16 − measured_I) / 20)      // level_sc 로 넘긴다
```
- **들리는 소리에는 어떤 필터도 안 붙는다.** 감지 경로의 게인만 바뀐다.
- `loudnorm` 의 룩어헤드 지연이 감지 경로와 들리는 경로를 어긋나게 할 걱정도 없다.
- 결정적이다 — 같은 입력이면 같은 G.

**언제 이걸로 부족한가:** 나레이터가 속삭였다 외쳤다 하면(트리거 LRA > 12 LU) 고정 게인 하나로는
조용한 문장이 임계 아래로 떨어진다. 그때는 **감지 경로에만 `loudnorm` 을 건다**:
```
[2:a]asplit=2[vdet0][vout];
[vdet0]loudnorm=I=-16:TP=-1.5:LRA=11[vdet];
```
**⚠️ 확인 필요:** 이 경로에서 `loudnorm` 의 룩어헤드가 `[vdet]` 을 `[vout]` 대비 시간축으로 밀어
**더킹이 늦게 걸리는지.** 확인 방법: 알려진 시각(예: 정확히 3.000초)에 클릭음 하나만 있는 트리거로
믹스하고, **음악이 실제로 눌리기 시작하는 시각**을 샘플 단위로 잰다. 3.000초 − attack 이 아니면
지연이 있는 것이고, 그만큼 `adelay` 로 보정하거나 이 경로를 쓰지 않는다.

## threshold 역산 — 공식으로 잡고 실측으로 고친다

목표 감쇠 `D = −20·log10(amount)` dB. `sidechaincompress`(downward)의 감쇠는 대략
`(L_sc − T) · (1 − 1/ratio)` 이므로 `ratio = 4` 에서:
```
T_dB = L_sc − D / 0.75          (L_sc = level_sc 적용 후 감지 레벨 ≈ −16 dB)
T    = 10^(T_dB / 20)           // sidechaincompress 의 threshold 는 선형값 (0.000977..1)
```
**이 공식은 정확하지 않다.** W7 의 추천값 `threshold=0.05`(−26dB)를 넣으면 공식은 7.5dB 를
예측하는데 실측은 10.3dB 였다 — RMS 통합값보다 순간 피크가 높기 때문이다.

→ **믹스가 0.72초밖에 안 걸리므로 재서 고친다.**
1. 공식으로 T 를 잡고 한 번 믹스한다.
2. **B 에서 만든 파형 포락선으로 목소리 구간을 알고 있으므로**, 눌릴 스템의 원본과 믹스 결과를
   그 구간에서 각각 재서 **실제 감쇠**를 구한다.
3. 목표와 **1.5dB 넘게 차이 나면** `T_dB += (실제 − 목표)/0.75` 로 고쳐 **한 번만 다시 믹스**한다.
4. 최대 2회. 그래도 안 맞으면 그 사실을 잡 결과에 숫자로 남긴다.

**최대 추가 비용 0.72초 + 측정.** 사실상 공짜다.

## 미리보기는 볼륨 키프레임 근사 — 원칙 위반이 아니다

**PRD P3 = 「결과물 무타협, 미리보기는 프록시」.** 미리보기가 근사인 것은 **원칙 그 자체**다.
미리보기는 540p 프록시를 쓰고, 배속을 16으로 클램프하고, 볼륨을 1로 클램프한다.
**더킹도 같은 범주다 — 렌더는 진짜 컴프, 미리보기는 B 의 키프레임.**

**숨기지 않는다.** 더킹 패널에 항상 배지를 띄운다:
> 미리보기: 키프레임 근사 · 렌더: 사이드체인 컴프

그리고 검증 8번에서 **둘이 얼마나 다른지 dB 로 재서 문서에 적는다.** 사용자가 알아야 한다.

# B. 키프레임 더킹 개선 — 파형 포락선

## 지금 무엇이 문제인가

`packages/engine/src/apply.ts:663`:
```ts
const intervals = voice.clips.map((c) => ({ start: c.start, end: c.start + c.duration }));
```
**「목소리 클립이 놓여 있으면 그 구간 전부가 목소리」다.** 10초짜리 나레이션 클립 안에 3초의
숨 쉬는 구간이 있어도 **10초 내내 음악이 눌린다.** 알고리즘이 아니라 **입력 해상도**가 문제다.

## 파형을 고친다 — 1000버킷 고정 → 20ms 고정 + RMS

`packages/media/src/index.ts:83`:
```ts
const WAVEFORM_BUCKETS = 1000;   // 고정
```
- **60초 클립이면 버킷당 60ms.** 한국어 음절이 100~200ms 이니 아슬아슬하다. 5분이면 버킷당 300ms —
  더킹 판정에 못 쓴다.
- **최댓값(peak) 기준**이라 한 번 튄 클릭 잡음이 버킷 전체를 「말하는 중」으로 만든다.

### 바꿀 것

```ts
const WAVEFORM_BUCKET_MS = 20;      // 8kHz mono → 버킷당 160 샘플
const WAVEFORM_MAX_BUCKETS = 20000; // 400초를 넘으면 버킷 시간을 늘린다
// bucketMs = max(20, ceil(durationMs / 20000))
```
- **peak 과 RMS 를 둘 다 저장한다.** 같은 루프에서 계산되므로 비용이 같고,
  **UI 파형 그리기는 peak** 이 보기 좋고(파형이 살아 보인다) **더킹 판정은 RMS** 가 맞다.
- 크기: 60초 = 3000버킷 × 2배열 ≈ **36KB**. 상한(20000버킷)에서도 **240KB**.

### 파일 형식 — 하위호환

```jsonc
// 옛 형식 (배열)          [0.1, 0.3, ...]                 ← 1000개 peak
// 새 형식 (객체)          { "bucketMs": 20, "peaks": [...], "rms": [...] }
```
읽는 쪽은 `Array.isArray()` 로 가른다.
**옛 형식 파일은 더킹에 쓰지 않는다.** 버킷 시간을 알 수 없어 시각을 계산할 수 없다.
→ `bucketMs` 가 없으면 **waveform 잡을 다시 등록한다.** (PCM 디코드라 60초에 0.2초 — 싸다.)
**조용히 근사해서 쓰지 않는다.**

## 목소리 구간을 뽑는 순수 함수

```ts
// packages/engine/src/duck.ts 에 추가 (기존 duckKeyframes 는 손대지 않는다)
export type VoiceEnvelope = { bucketMs: number; rms: number[] };

export function voiceIntervalsFromEnvelope(
  clips: readonly (AudioClip | VideoClip)[],
  envelopes: Record<string /* assetId */, VoiceEnvelope>,
  opts: {
    thresholdDb?: number;     // 미지정이면 적응형 (아래)
    sensitivityMs: number;    // 이보다 짧은 «틈»은 말이 이어지는 것으로 본다. 기본 300
    minSpeechMs: number;      // 이보다 짧은 «말»은 무시. 기본 120
  },
): DuckInterval[];
```

**`duckKeyframes` 는 수정하지 않는다.** 이미 `DuckInterval[]` 을 받는 순수 함수라
**구간을 어떻게 만드느냐만 바뀐다.** 엔벨로프·합집합·교점 계산은 전부 그대로 쓴다.

### 임계 — 적응형이 기본이다

**고정 임계(예: −40 dBFS)를 기본으로 하면 A 에서 겪은 것과 똑같은 함정에 빠진다** —
조용한 녹음에서는 아무것도 안 잡힌다.

→ **적응형:** 클립이 실제로 쓰는 구간(`in`~`out`)의 0 아닌 RMS 중 **상위 10% 지점(90퍼센타일)을
「말하는 레벨」로 보고 거기서 −25dB** 를 임계로 한다. 녹음 레벨과 무관해진다.
`thresholdDb` 를 명시하면 그 값을 쓴다(수동 노브도 남긴다).

### 기본값의 근거

| | 값 | 근거 | 상태 |
|---|---|---|---|
| `sensitivityMs` | 300 | 한국어 어절 사이 쉼 50~200ms, 문장 사이 300~600ms. 300이면 어절은 메우고 문장은 살린다 | **⚠️ 확인 필요 — 실제 나레이션으로 재야 한다** |
| `minSpeechMs` | 120 | 기침·마우스 클릭·립노이즈를 거른다 | ⚠️ 같이 잰다 |
| 적응형 −25dB | — | 말소리와 숨소리 사이 폭 | ⚠️ 같이 잰다 |

**확인 방법:** 실제 한국어 나레이션 3개(빠른 광고 톤 / 보통 / 느린 브랜드 톤)의 엔벨로프에서
「틈」의 길이 분포를 히스토그램으로 그린다. 어절 틈과 문장 틈 사이의 골짜기가 `sensitivityMs` 다.

### 구현할 때 반드시 맞출 것

- **파형은 소스 파일 기준, 구간은 타임라인 기준이다.** `clip.in` · `clip.speed` · `reversed` 를
  반영해야 한다. `speedRamp` 가 있으면 **`rampSegments(clip)` 로 세그먼트별로 변환**한다
  (등속 가정으로 계산하면 램프 구간에서 최대 수백 ms 어긋난다).
- **`clip.volume === 0` 이거나 트랙이 `muted` 면 건너뛴다.** 안 들리는 소리가 더킹을 일으키면 안 된다.
- 파형은 원본 레벨이므로 **클립 볼륨·페이드는 반영하지 않는다** — 다만 위 0/muted 는 거른다.

## UI — `DuckDialog.tsx` 확장

Premiere 와 같은 세 값을 노출한다:
```
음악 트랙       [ 음악 ▾ ]
목소리 트랙     [ 나레이션 ▾ ]
감쇠량          [====●======] 원래의 25% (−12dB)
민감도          [======●====] 300ms   말 사이 이만큼의 틈은 이어진 것으로 봅니다
페이드          [===●=======] 400ms   내려가고 올라오는 시간
──────────────────────────────
□ 진짜 사이드체인 컴프로 렌더 (렌더 시간 약 2.2배 — 5초 기준 22초 → 48초)
   미리보기는 키프레임 근사입니다
```
- **감쇠량에 dB 를 병기한다.** 어느 쪽 언어를 쓰든 읽힌다.
- 「페이드」 하나로 attack/release 를 묶는다(Premiere 의 Fade Duration). 따로 만지고 싶으면
  기존 두 칸을 「고급」 접이식으로.
- 체크박스를 켜면 `Track.duckedBy`/`duck` 을 설정한다. **끄면 키프레임만.**
  **둘 다 켜져 있으면 렌더 시 키프레임 볼륨은 무시하고 사이드체인만 적용한다** — 안 그러면
  이중으로 눌린다. (스템 렌더 시 눌릴 트랙의 volume 키프레임을 제거한 doc 사본을 쓴다.)

## 진짜 컴프와 티가 나는 3가지

1. **말 사이 짧은 틈** — 잘못 고르면 단어마다 음악이 펄떡인다. Premiere 에 Sensitivity 가 있는
   이유다. 진짜 컴프는 release 시상수가 이걸 자연히 처리한다.
2. **말이 시작되는 순간의 곡선** — 키프레임 이징이 4종뿐이라 컴프의 지수 곡선과 다르다.
   → **S2 의 베지어 이징이 이걸 개선한다.** attack 램프에 「강한 감속」 `(0.19,1,0.22,1)` 을
   쓰면 컴프에 훨씬 가까워진다. **B 를 만들 때 attack/release 램프의 이징을 선형에서 이 곡선으로
   바꾼다**(지금은 `easing: 'linear'` 고정 — duck.ts:96).
3. **음악이 이미 조용한 구간** — 진짜 컴프는 threshold 아래면 안 건드리는데 키프레임은 무조건
   내린다. 조용한 브리지에서 음악이 사라진다.
   → 고칠 수 있다(음악 클립의 포락선도 읽어 조용한 구간은 감쇠를 줄인다). **이번엔 안 한다.**
   포기가 아니라 순서다 — B 의 기본이 자리 잡고 검증 7번의 숫자를 본 뒤 정한다.

**티가 안 나는 경우 = 전형적인 15~30초 광고.** Premiere 가 키프레임으로 처리하는 바로 그 케이스다.

## 검증 — 숫자로 낸다

**1. W7 실증 재현 (A)** — 목소리가 3~7초에만 있는 10초 프로젝트를 렌더해 구간별 dB:
0~2초 −12.2 **그대로**(±0.3dB) · 4~6초 **−15.6**(±0.5dB) · 8~10초 −12.1 **그대로**(±0.3dB).

**2. 목표 감쇠 정확도 (A)** — `duck.amount` 를 0.5(−6dB)·0.25(−12dB)·0.125(−18dB)로 두고
실제 감쇠를 재서 **±1.5dB 안**에 드는지. 2회 믹스 보정을 켠 상태와 끈 상태를 각각 잰다.
**보정 없이도 ±1.5dB 면 보정 로직을 안 넣는다.**

**3. 조용한 녹음 함정 (A)** — 나레이션 진폭을 0.1 로 줄여도 **목표 감쇠가 유지되는지.**
W7 실측의 −0.1dB 가 아니라 −12dB 근처가 나와야 한다. `level_sc` 가 동작하는지의 시험이다.
트리거 LRA 가 넓은 소스(속삭임+외침)도 같이 잰다 — 여기서 실패하면 감지 경로 `loudnorm` 으로 간다.

**4. 스템 격리 (S5 검증과 짝)** — `renderAudioStem` 이 지정한 트랙만 담는지.
**다른 트랙 소리가 −90dB 이하**여야 한다.

**5. 길이 일치** — 스템 wav 와 영상 mp4 의 길이가 **1프레임(33ms) 이내**인지. 같은 `renderMedia`
프레임 수에서 나오므로 같아야 한다. 다르면 `amix duration` 처리를 다시 본다.

**6. 비용** — 5초 실측(22.24 / 12.71 / 12.71 / 0.72 = 48.4초, 2.2배)이 **30초 광고에서도 유지되는지.**
유지되면 UI 의 예상 시간 계산에 그 계수를 쓴다.

**7. 파형 포락선 개선 (B)** — 나레이션 클립 **한가운데에 3초 무음**을 넣고:
- 개선 전: 10초 내내 눌림
- 개선 후: **그 3초에 음악이 안 눌려야** 한다 (음악 레벨이 원래의 ±0.5dB 안)

**8. 파형 해상도 (B)** — **100ms 짜리 음절 하나**를 검출하는지. 1000버킷 고정(60ms 버킷)에서는
놓칠 수 있었다. 20ms 버킷으로 잡히는지 확인한다. 옛 형식 파일을 만나면 **다시 굽는지**도 확인.

**9. 미리보기 vs 렌더 차이를 숫자로** — 같은 프로젝트를 키프레임 근사와 진짜 사이드체인으로 각각
만들어 **구간별 dB 차이를 표로** 만든다. 「티가 나는 3가지」가 실제로 얼마나 다른지 재고,
그 표를 이 문서에 남긴다. **사용자가 어느 쪽을 쓸지 정하는 근거다.**

**10. 순환·자기참조 거부** — `duckedBy` 자기 자신, A→B→A 순환이 `BAD_DUCK` 으로 막히는지.

## 하지 않을 것

- **미리보기가 다르다는 이유로 진짜 사이드체인을 안 만들지 않는다.** PRD P3 그대로다.
  (이걸로 이미 한 번 틀렸다.)
- **렌더가 2.2배라고 기본값으로 켜지 않는다.** 켤지는 사용자가 정하고, 예상 시간을 미리 보여준다.
  반대로 **「느리니까 안 만든다」도 하지 않는다.**
- **키프레임 더킹을 「가짜」라고 버리지 않는다.** Premiere 와 같은 방식이고, 15~30초 광고에서는
  티가 안 난다. 대신 입력 해상도를 고친다.
- **조용한 녹음 함정을 「사용자가 알아서 크게 녹음하면 된다」로 넘기지 않는다.**
  `level_sc` 로 자동 보정하고, 검증 3번에서 실제로 되는지 잰다.
- **들리는 나레이션에 `loudnorm` 을 몰래 걸지 않는다.** 조사안의 필터그래프는 그렇게 되어 있고,
  그건 사용자가 맞춰 놓은 나레이션 크기를 덮어쓴다.
- **파형 형식을 바꾸면서 옛 파일을 조용히 근사해 쓰지 않는다.** 다시 굽는다.
- **「전체 믹스에서 목소리 스템을 표본 단위로 빼면 스템 1장으로 된다」(W7 의 미검증 아이디어)를
  검증 없이 쓰지 않는다.** 성립할 것으로 보이지만 재지 않았다. 하려면 F17 에서
  **뺀 결과와 실제 스템의 표본 차이를 재고**(−90dB 이하여야 한다) 넣는다.
- **「음악이 조용한 구간」 개선(티 나는 경우 3)을 이번에 끼워 넣지 않는다.** 검증 9번의 숫자를
  보고 다음에 정한다.
