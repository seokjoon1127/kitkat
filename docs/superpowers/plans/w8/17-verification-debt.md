## V3. `@remotion/motion-blur` 는 비디오를 못 흐린다 — **명제 맞음**

### 어떻게 쟀나
- 소스 영상: 1280×360, 30fps, 흰 원(반지름 20)이 **프레임당 정확히 40px** 이동. h264 `crf 0`(무손실).
  검증: 프레임 15 에서 x 621–659, 프레임 16 에서 x 661–699 — 딱 40px.
- 같은 프레임(15·30·45)을 `renderStill` 로 PNG 로 뽑아 픽셀 비교.
- 비교군 3종: ① `<OffthreadVideo>` ② 켄번스 줌(정지 이미지 `scale` 을 프레임당 2%씩)
  ③ 순수 CSS `translateX` 로 프레임당 40px 움직이는 흰 원(비디오가 아닌 대조군).

### 실측

| 비디오, 감싼 것 vs 안 감싼 것 (셔터 180°·샘플 10) | **0.0000** | **0** | **0 (0.000%)** |
| 비디오, 셔터 **360°**·샘플 **20** | **0.0000** | **0** | **0 (0.000%)** |
| 켄번스 줌 f15 | 90.90 | 255 | 300,383 (65.2%) |
| 켄번스 줌 f30 | 62.98 | 255 | 242,349 (52.6%) |
| 켄번스 줌 f45 | 46.31 | 255 | 202,621 (44.0%) |

**가장자리 프로파일 (y=180, 밝기 32 이상인 구간의 폭):**

| | 폭 | 위치 |
|---|---|---|
| 비디오 원본 f15 | 39px | 621–659 |
| 비디오 + 블러 180° | **39px** | **621–659 (완전히 동일)** |

**라플라시안 분산(낮을수록 흐림):** 켄번스 줌 f15/30/45 = 10191.9 / 5498.5 / 3292.7 →
블러 걸면 5625.2 / 3749.7 / 2556.9 = **45% / 32% / 22% 감소**. 트랜스폼에는 확실히 걸린다.

### 왜 그런가 — 원본 코드 + 실측으로 확인
`CameraMotionBlur.js` 는 `<Freeze frame={현재프레임 − (셔터/360)·(k/N) + 1}>` 을 N장 겹친다.
즉 샘플 구간은 **`[프레임 + 1 − 셔터/360,  프레임 + 0.95]`** 다.
셔터 360° 여도 폭이 **정확히 컴포지션 한 프레임**이라, 소스 fps 와 컴포지션 fps 가 같으면
**샘플 N개가 전부 같은 소스 프레임**에 떨어진다. 같은 그림 N장을 `plus-lighter` 로 1/N 씩
더하면 원본과 **비트 단위로 같아진다** — 그래서 차이가 0 이다.

**확인 사살:** 소스만 60fps 로 바꿔(컴포지션은 그대로 30fps) 다시 쟀다.

| | 폭@32 | 위치 | 달라진 픽셀 |
|---|---|---|---|
| 원본 f15 | 39px | 621–659 | — |
| 블러 180° | 39px | **641–679** | 1,520 |
| 블러 360° | 59px | 621–679 | 1,520 |

180° 에서는 **번지지 않고 20px 통째로 밀리기만** 했고, 360° 에서야 소스 프레임 2장이 잡혀
**두 겹 잔상**(부드러운 번짐이 아니다)이 됐다. 즉 잡히는 소스 프레임 수 ≈
`셔터각/360 × (소스fps ÷ 컴포지션fps)` 이고, 30/30 에서는 **항상 1** 이다.

### 덤으로 나온 것 — 블러가 「앞으로」 간다
코드의 `+1` 때문에 샘플 구간이 현재 프레임보다 **미래**다. CSS 상자로 재 보면
원본 중심 639.5px → 블러 중심 668.5px, **+29px = +0.725 프레임 앞서 있다.**
`<CameraMotionBlur>` 는 흐리기만 하는 게 아니라 **물체를 0.7프레임 앞으로 옮긴다.**
→ **F3-B 의 자체 구현(B-1)은 `[t − 셔터, t]` 로 「뒤쪽」을 샘플링해야 한다.** 그게 실제 카메라다.

### 그래서 뭘 해야 하나
**계획 그대로 F3-B 는 B-1(자체 구현)으로 간다.** `@remotion/motion-blur` 를 넣어도 A(소스 영상
피사체)는 0% 해결되고, B(트랜스폼)만 되는데 그건 B-1 이 의존성 0으로 더 잘 한다(프레임 추출이
N배로 늘지 않고, 시간 방향도 맞출 수 있다). **A 는 ffmpeg 파생(F3-A)만이 답이다.**

## V5-2. `@remotion/media <Video>` 가 4가지를 견디는가 — **한 곳에서 깨진다**

### 어떻게 쟀나
프레임마다 자기 번호를 6비트 바코드로 그린 640×200 / 30fps / 64프레임 영상.
디코더를 소스로 검증(0→0, 1→1, 10→10, 31→31, 63→63). kitkat `clips.tsx` 의 구조를 그대로 옮겨
`<OffthreadVideo>` 판과 `@remotion/media <Video disallowFallbackToOffthreadVideo>` 판을 각각
30프레임 렌더하고 **프레임마다 어느 소스 프레임이 나왔는지** 대조했다.

### 실측 — 30프레임 판독값
| 조합 | `<OffthreadVideo>` | `@remotion/media <Video>` | 같은가 |
|---|---|---|---|
| 그냥 재생 | 0,1,…,29 | 0,1,…,29 | 같음 |
| **speedRamp** (kitkat `rampSequences` 값 그대로: 2배속 15프레임 + 0.5배속 15프레임) | 0,2,…,30,30,31,31,…,37 | 완전히 동일 | 같음 |
| **reverse** (역방향 파생 파일) | 63,62,…,34 | 완전히 동일 | 같음 |
| **loop** (`<Loop 10>` + trim 0–10, 1배속) | 0…9 ×3 | 완전히 동일 | 같음 |
| **freeze** (`<Freeze 12>` + trim 0–13) | 12 ×30 | 완전히 동일 | 같음 |
| reverse + speedRamp | 63,61,…,33,33,32,…,26 | 완전히 동일 | 같음 |
| reverse + freeze | 51 ×30 | 완전히 동일 | 같음 |
| **loop + 2배속** (`<Loop 10>` + trim 0–10, rate 2) | 0,2,4,…,18 ×3 | **0,2,4,6,8, 빈화면×5** ×3 | **다름** |
| **2배속 + 좁은 trim** (trim 0–10, rate 2, 30프레임 표시) | 10프레임(0…18) 뒤 빈화면 | **5프레임(0…8) 뒤 빈화면** | **다름** |

「빈화면」은 배경색만 남은 상태다(평균휘도가 배경 `#004400` 의 40.0 과 정확히 일치, 흰 띠 0개).

### 원인 — `trimAfter` 의 「뜻」이 다르다
- `<OffthreadVideo>`: `trimAfter − trimBefore` 는 **타임라인에서 보이는 프레임 수**다.
  `playbackRate` 는 그 안에서 소스를 빨리 훑을 뿐이라 보이는 길이가 안 줄어든다.
- `@remotion/media <Video>`: `trimAfter` 는 **소스 위치의 상한**이다.
  보이는 길이 = `(trimAfter − trimBefore) ÷ playbackRate`. 배속을 올리면 **꼬리가 조용히 사라진다.**

### kitkat 은 지금 안 걸린다 — 하지만 우연이다
`mediaTrimFrames` 가 `trimAfter = max(trimBefore+1, msToFrames(outMs), trimBefore + 표시프레임)`
이고 `msToFrames(outMs) = trimBefore + 표시프레임 × 배속` 이라, 트림 구간이 항상
`표시프레임 × 배속` 이상이다. **위 표의 speedRamp 행은 kitkat 의 실제 인자 그대로 넣은 것이고
둘이 완전히 같았다.** 하지만 이 불변식은 코드 어디에도 안 적혀 있다 —
`trimAfter` 를 조금이라도 줄이면 `<Video>` 쪽만 소리 없이 뒷부분이 빈다.

### 확인 못 한 것 (구체적으로)
- **소리.** 테스트 영상에 오디오 트랙이 없어 못 쟀다. 다만 `clips.tsx` 를 읽어 보니 kitkat 은
  영상 요소를 전부 `muted` 로 깔고 **소리는 remotion 코어 `<Audio>` 로 따로 깐다.**
  즉 `<OffthreadVideo>` → `<Video>` 교체는 오디오 경로를 건드리지 않는다.
- `preservePitch`, 알파(투명) 영상, 톤매핑(HDR) — 이번 범위 밖이라 안 쟀다.

### 그래서 뭘 해야 하나
**교체는 가능하다. 단 조건 두 개를 문서에 박아라:**
1. `trimAfter − trimBefore ≥ 표시프레임 × 배속` 을 **불변식으로 명시**하고 `mediaTrimFrames` 에
   주석 + 단위테스트로 못 박는다(지금은 우연히 맞고 있을 뿐이다).
2. 바꾸면 위 9가지 조합의 **프레임 판독 대조를 회귀 테스트로 남긴다** — 이 실험 그대로 하면 된다.

## V5-3. `mask: url(#id)` + `mixBlendMode` + 부모 `transform` — **명제 틀림. 안 어긋난다**

### 어떻게 쟀나
640×200 흰 판에 SVG `<mask>`(검은 전면 사각 + 흰 100×100 사각을 (200,50)에) 를 걸고,
부모에 `transform: rotate(20deg) scale(1.4)`, `transform-origin: 320px 100px` 를 준다.
`mixBlendMode: plus-lighter` 를 켠 판·끈 판을 각각 무손실 PNG 로 렌더.
**변환이 마스크에도 걸릴 때의 사각형 꼭짓점을 손으로 계산**해 두고
(186.1,−23.2) (317.6,24.6) (269.7,156.2) (138.2,108.3) = 화면 안 18,757px,
실제 흰 픽셀과 겹침 정도(IoU = 교집합÷합집합)를 쟀다.

| 조합 | 흰 픽셀 | 경계상자 | 「변환이 걸린다」 예상과 IoU | 「화면좌표에 고정」 예상과 IoU |
|---|---|---|---|---|
| `mask:url(#m1)` 만 | 10,000 | (200,50)–(299,149) | 0.414 | **1.000** |
| `mask` + `mixBlendMode` | 10,000 | 동일 | 0.414 | **1.000** |
| `mask` + 부모 변환 | 18,634 | (139,0)–(316,155) | **0.993** | 0.414 |
| `mask` + 변환 + `mixBlendMode` | 18,634 | **완전히 동일** | **0.993** | 0.414 |
| kitkat 방식(`maskImage` 그래디언트) + 변환 | 18,757 | (138,0)–(316,155) | **1.000** | 0.414 |
| kitkat 방식 + 변환 + `mixBlendMode` | 18,757 | **완전히 동일** | **1.000** | 0.414 |

- 변환이 없으면 마스크는 **정확히 (200,50)–(299,149)** — 1픽셀도 안 어긋난다.
- 변환이 있으면 마스크가 **변환을 정확히 따라간다**(kitkat 방식은 IoU 1.000, `url(#id)` 는 0.993).
  0.993 의 부족분 123픽셀은 **가장자리 안티에일리어싱**(내 판정 기준이 「RGB 200 초과」라
  반쯤 덮인 픽셀이 빠진다)이지 어긋남이 아니다 — 경계상자가 1px 차이다.
- **`mixBlendMode` 는 어느 경우에도 좌표를 1픽셀도 안 바꿨다.**

### 대신 진짜 함정을 하나 찾았다
처음 만든 판은 `<mask>` 에 `x/y/width/height` 를 안 주고 `<svg width={0} height={0}>`(viewBox 없음)
안에 넣었다 → **마스크 걸린 요소가 통째로 사라졌다**(흰 픽셀 0개, 오류 메시지도 없음).
마스크 영역의 기본값이 백분율(−10%/−10%/120%/120%)이라 **0×0 뷰포트에서 0×0 으로 접힌다.**
`<mask x y width height>` 를 명시하고 `viewBox` 를 주면 width/height 0 인 svg 안에서도
정상 동작한다(흰 10,000px 확인).

### 그래서 뭘 해야 하나
**F9(자유 마스크)에서 `clip-path`·`url(#id)` 를 써도 좌표 걱정은 안 해도 된다.**
다만 마스크를 담는 `<svg>` 에는 **`viewBox` 와 `<mask>` 의 `x/y/width/height` 를 반드시 명시**하라 —
안 그러면 조용히 사라진다. 이 한 줄을 `svg-filters.tsx` 옆에 주석으로 남기는 게 좋다.

### 세 가지 결론
1. **사람 목소리는 확실히 다르게 나온다 — 같은 피크에서 2.1dB 덜 눌린다**(−11.8 vs −13.9).
   **원인은 스펙트럼이 아니라 크레스트 팩터(피크 대비 실효값)다.** 같은 피크 1.00 에서
   나레이션의 LUFS 가 핑크 노이즈보다 **2.7dB 낮다**(−15.6 vs −12.9). 컴프는 실효값을 보므로
   딱 그만큼 덜 눌린 것이다. **라우드니스를 맞추면 차이가 0.3~0.4dB 로 사라진다**(위 표 오른쪽 열).
2. **kitkat 의 지금 설계(`level_sc` 로 감지 경로를 −16 LUFS 에 정렬)가 이 문제를 이미 없앴다.**
   녹음 레벨이 13dB 범위로 흔들려도 깊이는 **0.2dB 안**에서만 변한다. W7 이 경고한
   「조용히 녹음하면 더킹이 아예 안 걸린다」는 해결됐다.
3. **그런데 열린 고리(공식) 자체가 어긋난다.** 「−12dB」로 설정했는데 첫 시도가
   **−14.1dB(나레이션) / −14.4dB(핑크)** — **2.1~2.4dB 더 깊다.** 허용오차
   `DUCK_TOLERANCE_DB = 1.5` 를 넘는다. 그런데 `sidechain.ts` 주석에 적힌 이 컴퓨터 실측은
   같은 threshold(−32.05dB)에서 **−7.1dB(4.9dB 얕음)** 이다 — **부호가 반대다.**
   즉 공식의 오차는 상수가 아니라 **소재에 따라 ±2.5dB 이상 흔들린다.**

### 그래서 뭘 해야 하나
**`nextThresholdDb` 의 재서-고치는 고리를 절대 빼지 마라.** 「실측으로 상수를 튜닝해서
한 번에 맞추자」는 안 된다 — 소재에 따라 오차 부호가 뒤집힌다.
`MAX_DUCK_ATTEMPTS = 4` 와 할선법(두 점 기울기)을 그대로 두는 게 맞다.
표(W7 §9 의 「목소리 진폭 → 더킹 깊이」)는 **「`level_sc` 도입 전 이야기」라고 표시**하고
위 오른쪽 열로 갱신하는 게 좋다.

## V5-6. 「전체 − 목소리 = 음악」 — **명제 맞음. 비트 단위로 정확히 0**

### 어떻게 쟀나
kitkat `renderAudioStem` 의 솔로 방식을 그대로 옮긴 Remotion 프로젝트:
코어 `<Audio>` 두 장(목소리 = speech.wav 8초, 음악 = 핑크노이즈+220Hz), 각각
**프레임마다 값이 바뀌는 `volume` 함수**를 걸고 `codec:'wav'` 로 3번 렌더 —
① 전체 ② 목소리만(음악 muted) ③ 음악만(목소리 muted). 240프레임 / 30fps / 48kHz 스테레오.

### 실측 — 포화(클리핑) 없을 때
| 지표 | 값 |
|---|---|
| 표본 수 | **768,000** (8.000초 스테레오) |
| 전체 피크 | −10.40 dBFS (포화 없음) |
| 목소리 RMS / 음악 RMS | −27.91 / −34.76 dBFS |
| 음악 스템 RMS | −34.76 dBFS |
| 잔차(전체 − 목소리) RMS | −34.76 dBFS |
| **차이(잔차 − 음악) RMS** | **정확히 0** (모든 표본) |
| **차이 최대 절대값** | **정확히 0** |
| **상관계수** | **1.000000000** |
| 목소리가 실제로 있는 표본(진폭 0.01 초과) | 315,356개 — 그 구간에서도 오차 0 |
| 참고: 16비트 1LSB | 3.05e−5 = −90.3 dBFS |

**이유:** Remotion 은 트랙마다 wav 를 따로 굽고(필터는 `volume` 하나) 그걸 **정수 덧셈**으로 섞는다.
출력이 16비트 PCM 이고 리미터도 디더도 없으므로 `전체 = 양자화(목소리) + 양자화(음악)` 이 **항등식**이다.

### 하지만 조건이 셋이다 — 전부 실측했다

**조건 1. 합이 0 dBFS 에 닿으면 깨진다.** 두 트랙을 3.2배로 올려 다시 렌더(768,000 표본 중
**538개(0.070%)가 포화**):

| 지표 | 값 |
|---|---|
| 차이 RMS | −53.75 dBFS (**음악 대비 −36.2dB**) |
| 차이 최대 | −10.47 dBFS |
| 상관계수 | 0.999880 |

→ 0.07% 만 포화해도 잔차에 들리는 쓰레기가 남는다. **전체 믹스는 어차피 굽는 것이니
피크가 0 dBFS 면 스템 2장으로 물러서면 된다 — 검사는 공짜다.**

**조건 2. 「전체」쪽이 손실 압축이면 못 쓴다.** 같은 wav 를 AAC 로 굽고 빼 봤다:

| 「전체」의 형식 | 차이 RMS | 음악 대비 | 최대 차이 |
|---|---|---|---|
| wav (무손실) | −400 dBFS | **−365 dB** | 0 |
| **aac 192k** | −52.3 dBFS | **−17.6 dB** | −29.6 dBFS |
| **aac 320k** | −64.8 dBFS | **−30.0 dB** | −31.9 dBFS |

→ **영상 렌더의 aac 오디오를 「전체」로 쓰면 안 된다.** 음악 대비 −17.6dB 면 그냥 들린다.
「전체」쪽도 **반드시 wav 로 따로** 뽑아야 한다.

**조건 3. 트랙 구성이 맞아야 한다.** kitkat 은 **특정 트랙 하나**(`duckedBy` 로 지정한 것)를 누른다.
`전체 − 트리거` 는 **「트리거 뺀 전부」**지 「눌릴 트랙」이 아니다.
둘이 같아지는 건 **문서의 오디오가 정확히 {트리거 트랙, 눌릴 트랙} 두 개뿐일 때**다.
(지금 흐름의 3번 렌더는 「두 트랙 muted 한 영상」이라, 다른 오디오 트랙이 있으면 거기 들어간다.)

### 아낄 수 있는 시간 (조건이 다 맞을 때)
`sidechain.ts` 의 `RENDER_SEC_PER_SEC`(영상 4.448 · 스템 4.2 · 믹스 0.144 초/초) 기준:
- 지금: 영상 + 스템×2 + 믹스 = **12.99 초/초** (보통 렌더의 **2.92배**)
- 뺄셈: 영상 + 스템×1 + 믹스 = **8.79 초/초** (보통 렌더의 **1.98배**)

→ **32% 단축.** 다만 조건 2 때문에 「전체 wav」를 따로 뽑아야 하므로,
실제 이득은 **「영상 렌더가 오디오를 wav 로도 같이 내놓을 수 있느냐」**에 달렸다.
그건 설계 결정이라 여기서 정하지 않는다.

### 그래서 뭘 해야 하나
1. **뺄셈 자체는 안전하다** — 비트 단위로 정확하다. 「될 것으로 보인다」를 「확인함」으로 바꿔라.
2. 도입하려면 **① 전체 믹스 피크가 0 dBFS 미만 ② 「전체」쪽이 wav ③ 오디오 트랙이 정확히 2개**
   — 이 셋을 **런타임에 확인하고, 하나라도 아니면 지금의 스템 2장으로 물러서게** 해라.
3. 셋 다 만족하기 어려우면 **지금 방식이 낫다.** 32% 는 조건 3개를 몰래 어길 만큼 크지 않다.

## 덤 — 하다가 걸린 것 하나

`<Audio volume={프레임함수}>` 에서 **볼륨 값의 가짓수가 많아지면 렌더가 통째로 실패한다.**
Remotion 은 프레임별 볼륨을 ffmpeg 의 **중첩 `if()` 한 줄짜리 식**으로 내보내는데,
240프레임짜리 매끄러운 곡선(값이 소수점 셋째 자리까지 제각각)에서
`[Parsed_volume_2] Error when evaluating the volume expression` → `Error initializing filters` 로 죽었다.
같은 곡선의 진폭만 3배로 키웠더니(=반올림 후 값의 가짓수가 늘어) 재현됐고, 상수 볼륨으로 바꾸니 통과했다.
**F13(키프레임 아무거나)·F12 미리보기처럼 볼륨 곡선을 촘촘하게 만들 계획이 있으면
이 상한을 먼저 재 봐야 한다.** (이번 작업 범위가 아니라 정확한 상한까지는 안 쟀다.)

# 실측 뒤 처리 (본체가 고친 것 / 안 고친 것)

## 고쳤다 — 볼륨 곡선이 렌더를 통째로 죽이는 버그

V5 를 재는 과정에서 나온 「`<Audio volume={프레임함수}>` 의 ffmpeg `if()` 식이 터진다」를
**끝까지 재서 원인과 경계를 정확히 찾고 고쳤다.**

**경계(이 컴퓨터에서 ffmpeg 직접 실행):**

| 서로 다른 볼륨 값 | 중첩 깊이 | 결과 |
|---|---|---|
| 99개 | 98 | OK |
| **100개** | 99 | **실패** — `Missing ')' or too many args`, exit −22 |

**원인:** remotion 은 값 하나마다 `if()` 를 한 겹 중첩한다. 자기도 이걸 알아서
`roundVolumeToAvoidStackOverflow` 로 1/97 격자에 스냅하는데, **그 함수는 볼륨이 0..1 이라고
가정한다.** kitkat 의 볼륨은 클립 0..2 × 트랙 0..2 = **0..4** 라 격자 칸이 최대 389개가 된다.

**remotion 의 진짜 식 생성기로 잰 중첩 깊이:**

| 설정 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 볼륨 1.0 · 페이드 10초 | 98 ✅ | 98 ✅ (식이 **완전히 동일**) |
| **볼륨 1.2 · 페이드 5초** | **117 ❌** | 98 ✅ |
| 볼륨 2.0 · 페이드 4초 | 121 ❌ | 98 ✅ |
| 클립 2.0 × 트랙 2.0 · 페이드 10초 | 301 ❌ | 98 ✅ |

**볼륨을 1.2 로 올리고 5초 페이드인을 건다** — 아주 평범한 설정에서 렌더가 죽는다.

**고침** (`packages/renderer/src/composition/volume.ts` 신규):
최대치가 1을 넘을 때만 값을 **최대치의 1/97 격자**에 먼저 스냅한다. 그러면 remotion 격자를
거쳐도 가짓수가 98을 못 넘는다. 최대치 ≤ 1 이면 **아무것도 안 한다 — 보통 설정에서 회귀 0**
(테스트가 「식이 문자 하나까지 동일」을 확인한다).
속도 램프 경로는 세그먼트 크로스페이드를 곱한 **뒤에** 한 번 더 스냅한다(안 그러면 스냅이 풀린다).

**대가(실측, −20dB 위 구간):** 최대치 2.0 에서 0.63dB, 4.0 에서 1.31dB. 레벨 «점프»가 아니라
완만한 램프의 계단 크기라 안 들린다.

테스트 21개 (`packages/renderer/test/volume-ffmpeg-depth.test.ts`) —
그 중 8개는 **설치된 remotion 의 실제 함수**를 불러 중첩 깊이를 센다(옮겨 적기가 틀려도 잡힌다).

## 고쳤다 — V5-2 의 성질을 코드에 못 박음

`mediaTrimFrames` 의 `Math.max` 안 `msToFrames(outMs, fps)` 항이 두 컴포넌트의 뜻 차이를
막아 주고 있는데 **어디에도 안 적혀 있었다.** 주석 + 테스트 2개
(`ramp.test.ts`, 조합 216가지)로 못 박았다. 최적화한다고 지우면 테스트가 잡는다.

## 안 고쳤다 — V5-6 스템 뺄셈 (근거와 조건을 남긴다)

**수학은 확인됐다** (768,000 표본 오차 0, 상관계수 1.000000000). 그런데 kitkat 에 붙이려면
지금 구조에서 **실제로 절약이 안 생긴다:**

- 지금 3패스 = ① 트리거 스템(wav) ② 눌릴 스템(wav) ③ 영상(오디오 없음).
- 뺄셈을 쓰려면 「전체 믹스」가 **무손실**이어야 한다(aac 192k 는 잔차 −17.6dB 로 못 씀).
  → ③ 을 오디오 포함으로 굽되 `audioCodec: 'pcm-16'` 이어야 한다.
  **remotion 은 h264 + pcm-16 을 지원한다**(`supportedAudioCodecs.h264 = ['aac','pcm-16','mp3']`) —
  여기까지는 막힌 게 없다.
- **남은 진짜 위험은 포화(클리핑)다.** 지금은 목소리와 음악을 «더하기 전에» 각각 굽는다.
  뺄셈을 쓰면 둘을 **먼저 더한 뒤** pcm-16(정수)로 자르므로, 광고처럼 큰 소재에서 잘릴 수 있다.
  실측: **0.07%만 잘려도 잔차가 −36.2dB 로 들린다.**
- 조건 ③ 「오디오 트랙이 정확히 2개」도 걸린다. 3개 이상이면 「전체 − 목소리」에
  **더킹하면 안 되는 트랙까지 섞여 들어간다.**

**결론:** 이득은 렌더 2.92배 → 1.98배(32% 단축)로 크지만, 얻는 곳이 「더킹 쓰는 렌더」로 한정되고
잃을 수 있는 것이 **오디오 정확성**이다. 붙이려면 포화 검출 + 폴백 + 「스템이 비트 단위로 같은가」
테스트가 먼저다. **지금 안 붙인 이유는 어렵거나 귀찮아서가 아니라 위 위험 때문이며,
붙일 때 필요한 것은 전부 여기 적혀 있다.**

## 남은 것 — 라우드니스 목표 (V5-4 가 드러낸 것)

kitkat 은 **광고를 만드는 도구인데** 라우드니스가 −14 LUFS 하나로 고정돼 있다.
구글 광고 공식 규격은 **−24 LKFS ±2** 라 **10dB 초과**다.
스키마 범위(`-30..-9`)는 이미 −24 를 담을 수 있으니 **플랫폼별 프리셋과 UI 노출**만 하면 된다.
→ UI 파일을 다른 담당자들이 쓰고 있어 그들이 끝난 뒤에 붙인다.

### 실제 렌더로 끝까지 확인 (2026-09-02)

수식과 remotion 함수만이 아니라 **진짜 렌더**로 확인했다. 서버(5758)에 볼륨 1.2 · 페이드인 5초 ·
10초 클립(30fps)을 만들어 렌더 → **성공(68.6초)**. 고치기 전이면 이 조합이 중첩 117겹이라
`Missing ')' or too many args` 로 렌더가 통째로 죽는 설정이다.

나온 파일의 페이드 포락선을 1초 창으로 재서, 스냅이 소리를 망가뜨리지 않았는지 봤다:

| 구간 | 실측 mean_volume | 마지막 창 대비 | 선형 페이드 이론값 |
|---|---|---|---|
| 0~1초 | −42.0 dB | −18.5 dB | −19.1 dB |
| 1~2초 | −33.1 dB | −9.6 dB | −9.5 dB |
| 2~3초 | −28.7 dB | −5.2 dB | −5.1 dB |
| 3~4초 | −25.7 dB | −2.2 dB | −2.2 dB |
| 4~5초 | −23.5 dB | 0 dB | 0 dB |

**최대 어긋남 0.6dB**(제일 조용한 첫 창 — 거기선 소스 자체 레벨 변동이 더 크다).
페이드가 계단이 되거나 기울기가 바뀌지 않았다.

# 리뷰 뒤 재작업 (2026-09-03) — 「고쳤다」고 한 것을 다시 뜯어본 결과

## 리뷰 #2 — 볼륨 스냅의 «소리 오차 1.31dB» 는 계산값이었다 → 실제로 쟀다

440Hz 사인파(레벨 일정)에 8초 페이드인을 걸어 최대치 3가지로 렌더하고, 50ms 창으로 포락선을 읽었다.
최대치 1.0 은 스냅이 **안 걸리는**(no-op) 대조군이다.

| 최대치 | 기준 레벨 | 이상적 선형 램프 대비 최대 편차 | 인접 창 최대 계단 |
|---|---|---|---|
| **1.0 (대조군, 스냅 없음)** | −24.47 dB | −1.29 dB (0.90초) | 1.74 dB |
| 1.2 | −22.88 dB | −1.16 dB (1.07초) | 1.73 dB |
| **4.0 (클립 2 × 트랙 2)** | −12.43 dB | −1.29 dB (0.90초) | 1.68 dB |

**세 줄이 0.1dB 안에서 같다.** 즉 ±1.3dB 편차와 1.7dB 계단은 **remotion 이 원래 갖고 있는 1/97 격자 +
페이드 초반(전체의 11%, −19dB 지점)에서 50ms 창이 격자 두 칸을 걸치는 것**이고, 내 스냅이 얹는
추가 오차는 **측정 한계 아래**다. 기준 레벨 차이(+1.6dB, +12.0dB)는 20·log10(1.2)=1.58, 20·log10(4)=12.04 와
맞아 클립×트랙 배율이 제대로 걸린다.

**정정:** 앞서 「최대치 4.0 에서 1.31dB」라고 적은 것은 «스냅 격자 한 칸의 이론값»이지 «스냅이 더한 오차»가
아니었다. 실측으로는 **스냅이 더하는 오차를 구분할 수 없다.**

**`@remotion/media` 로 갈아타면 피할 수 있는가 — 아니다.** `@remotion/media` 의 `<Audio>` 도
`registerRenderAsset` 으로 볼륨 배열을 넘기고, 식으로 바꾸는 자리는 `@remotion/renderer` 의
`stringifyFfmpegFilter` → `ffmpegVolumeExpression` **한 곳**뿐이다. 컴포넌트를 바꿔도 같은 `if()` 중첩이다.
kitkat 층에서 막는 것이 맞는 자리다.

측정 도구: `scripts/…` 가 아니라 임시 폴더의 `envelope.mjs`(astats 50ms 창 → RMS 포락선). 재현 명령은
`node envelope.mjs <파일> <페이드초> 0.05`.

**영상 렌더와 스템 렌더의 음원 자체가 갈린다** — 뺄셈이 성립하지 않는다. 계획서가 못 짚은 조건이다.

**포화 폴백**(임계 0 — 한 표본이라도 잘리면 물러섬): 클립 2.0 × 트랙 2.0 에서 포화 **17.25%**,
그냥 뺐다면 잔차가 신호보다 16.7dB 아래로 **들린다**. 폴백은 **영상 재렌더 없이** 눌릴 스템만 굽는다.
잡 결과에 `sidechain.stemSubtract.{used, reason, clippedSamples, totalSamples}` 로 남는다.
(클립 2.0 «만»으로는 포화 0 — remotion 이 실제로 건 게인이 ~1.4배였다.)

**계획서가 틀렸던 것:** 「remotion 은 h264+pcm-16 지원」까지는 맞지만 **출력 확장자가 `.mkv`/`.mov` 여야 한다**
(`validateOutputFilename`). `.mp4` 로 주면 렌더가 통째로 죽는다. 중간 영상만 `.mkv` 로 굽고 `-c:v copy` 로 옮긴다.
포화 세기는 ffmpeg 필터로 못 한다 — `volumedetect` 의 `histogram_0db` 는 안 잘린 큰 표본까지 세고(1106 vs 실제 166),
`astats` 의 `Peak count` 는 한쪽 극만 센다. wav 를 흘려 읽으며 직접 센다.

## 그 과정에서 드러난 것 — **`muxSidechain` 이 원래 비결정적이다**
똑같은 입력·똑같은 명령을 4번 돌리면 결과가 **3가지**로 갈린다:

| 비교 | 첫 차이 시각 | 최대 오차 | 차 RMS |
|---|---|---|---|
| 같은 명령 재실행 (1 vs 2) | 3.840초 | 6673 | −32.69 dBFS |
| 같은 명령 재실행 (1 vs 3) | 3.755초 | 6673 | −35.48 dBFS |
| **3패스 vs 뺄셈** | 3.925초 | 6673 | **−36.01 dBFS** |

**경로 간 차이가 재실행 간 흔들림보다 작다** — 즉 뺄셈이 원인이 아니다. 차이는 항상 마지막 0.25초 안에서만 나고
최대 오차는 항상 6673. 범인은 `sidechaincompress`(순수 `amix` 3회는 md5 동일, `-filter_threads 1` 이면 5회 중 4회 동일).
**렌더할 때마다 끝 0.2초가 달라진다는 뜻이다.** 담당 밖이라 고치지 않고 남긴다 — 따로 볼 값어치가 있다.

# 역방향 마스크 추적 — 붙였다 (2026-09-03)

F10 이 「1080p 900프레임 = 5.6GB 라 실용적이지 않다」며 뺐던 것. **전제가 틀렸다** — 전부 올릴 필요가 없다.
영상은 뒤로 디코드할 수 없으므로(P/B 프레임이 앞에 기댐) **창 하나씩 앞으로 풀어 링에 담고 링 안에서만 뒤로 훑고,
창을 버리고 그 앞 창으로 옮긴다.** 링에는 ndarray 가 아니라 디코드된 VideoFrame 을 담고 변환은 추적 직전 한 장씩.

| 소스 | 방향·창 | ms/프레임 | 최대 RSS | 순방향 대비 |
|---|---|---|---|---|
| 1280×720 | forward | 14.62 | 117MB | — |
| | **backward 30** | **24.61** | **184MB** | **1.68배** |
| 1080×1920 | forward | 23.07 | 164MB | — |
| | backward 15 | 45.98 | 217MB | 1.99배 |
| | **backward 30** | **34.44** | **285MB** | **1.49배** |
| | backward 60 | 55.52 | 423MB | 2.41배 |
| 1080×1920 **GOP250** | backward 30 | 78.63 | 285MB | **2.59배** |

창 60 은 더 빨라야 하는데 오히려 느리다 — 프레임 버퍼 재사용이 무너지는 쪽이 헛디코딩 감소보다 크다.
**긴 GOP 가 역방향의 진짜 비용이다**(GOP250 에서 2.59배) — 창을 채우려고 매번 키프레임부터 다시 푼다.

**정확도:** 역방향이 순방향보다 평균 4~7% · 최대 1~10% 나쁘고 IoU 는 0.4% 낮거나 같다
(720p 2.32→2.48px, 1080×1920 3.86→4.02px). **양방향 전체는 오히려 더 좋다**(평균 2.34px · IoU 0.922) —
각 반쪽이 짧아 표류가 덜하다. 이음매(224→225→226) 이동량 11.8px 은 이웃 이동량 95분위(11.9px) 안이라 안 튄다.
실패 감지: 양방향 모두 **진짜 놓친 실패 0 · 거짓 실패 0**, 역방향 경계가 정답과 정확히 맞는다.

**그 과정에서 고친 것 — 순방향에도 있던 사고:** 대상을 완전히 놓치면 ViT 가 말이 안 되는 상자를 돌려주고
다음 프레임에서 **「29GB 할당 실패」로 프로세스가 통째로 죽었다.** 죽으면 사용자는 「어디서 놓쳤는지」 대신
「track.py 실행 실패」만 본다. 이제 0 크기 상자·점수 0 으로 기록하고 계속한다.

**기본값은 `forward` 로 뒀다 — `both` 가 아니다.** 「여기서 다시 추적」 버튼이 툴팁으로 **「앞쪽 키프레임은 그대로
둡니다」**를 약속하는데, 기본을 `both` 로 하면 그 약속을 어기고 이미 만든 앞쪽을 덮어쓴다. 양방향은 UI 가
명시적으로 켠다(버튼 「여기서 앞뒤로 추적」 추가 — 기존 두 버튼의 뜻은 안 바꿨다). `both` 는 파이썬을 두 번 부르고,
**판정은 패스마다 따로** 한다 — 「3연속 실패 뒤 sticky」가 «추적 순서» 규칙이라 시간순으로 먼저 이으면 역방향이 뒤집힌다.

# 펜 마스크·여러 장 겹치기 — 빠른 미리보기가 그린다 (2026-09-03)

셰이더에서 베지어를 래스터화하지 않았다. 오프스크린 Canvas2D 에 `new Path2D(d)` 를 그려 **알파 텍스처 한 장**으로
굽고 셰이더가 `uMaskKind = 4` 로 곱한다(`ui/src/preview/mask-raster.ts` 신규). **무엇을 그릴지는 전부 렌더러의
`maskLayerCss()` 가 낸 것을 읽어서 정한다** — 미리보기가 수식을 다시 쓴 곳이 없다.
`clip-path: path()` → `ctx.clip()`, SVG `<mask>`+`feGaussianBlur` → `filter: blur(σpx)`,
반전(`feFuncA table "1 0"`) → 번진 «뒤에» 흰 전면을 `xor`, `mask-composite` → `source-over/out/in`(아래에서부터).

**페더 블러는 보정 없이 맞았다** — feather 0.1 평균 0.03·최대 2, feather 0.3 평균 0.01·최대 1.
여유(pad)는 렌더러와 같은 `max(2, 3σ)` 인데 **96px 에서 끊었다**(안 끊으면 1080×1920 페더 0.5 가 38MiB 텍스처).

| 케이스 | 평균 | 최대 | 통과 |
|---|---|---|---|
| path feather 0 / 0.001 / 반전 feather 0 | 0.05 / 0.05 / 0.06 | **52 / 55 / 57** | **X** |
| path feather 0.1 / 0.3 / 반전 0.2 | 0.03 / 0.01 / 0.09 | 2 / 1 / 2 | O |
| 2장 add / subtract / intersect | 0.01 / 0.00 / 0.01 | 1 / 2 / 2 | O |
| 3장 접힘 · dKeys 중간 · 직선 AA 기준자 | 0.04 / 0.02 / 0.00 | 2 / 1 / 1 | O |
| 회귀: rect / circle / linear | 0.03 / 0.03 / 0.04 | 1 / 1 / 1 | O (이전 0.04/1) |

**못 맞춘 것(숨기지 않는다):** 페더 0 자유 곡선의 **곡선 윤곽 1px 줄**에서 최대 52~57. 화면 평균은 0.05~0.06
(임계의 1/50), 12 넘는 픽셀은 0.17~0.24% 로 전부 윤곽선 위. 원인을 픽셀로 추적 — 브라우저의 두 채우기 경로가
**세로로 약 0.1px 어긋난다**(위쪽 윤곽은 미리보기가 덜 덮고 아래쪽은 반대 = 부푼 게 아니라 밀린 것;
반전 케이스에서 두 값의 합이 밑색과 정확히 일치하므로 반전·합성 자체는 맞다). **직선 변만 있는 기준자는
평균 0.00 · 최대 1 로 완전 일치** — 곡선에서만 갈린다. `fill()`→`clip()`, `willReadFrequently` 둘 다 효과 없었고,
0.1px 손 보정은 **넣지 않았다**(크롬 버전이 바뀌면 틀린 값이 된다).

**fps·재사용**(같은 실행 안에서, 150프레임): 마스크 없음 36.4 · rect 33.0 · path 고정 31.9(**재사용 99.3%**) ·
3장 겹침 32.3(99.3%) · `dKeys` 애니메이션 25.1(0%). **단일 패스 회귀 없음** — 늘어난 건 그리기당 GL 상태 호출
3개뿐이고 픽셀 셰이더 비용 0(`maskAlpha` 는 `uMaskKind > 0` 안에만 있다). 그 3줄 A/B: 35.5 vs 36.3 fps(실행 편차 안).

배지에서 「자유 곡선 마스크(미지원)」·「마스크 여러 장(미지원)」이 빠졌다. 실측표에 `maskPath`(평균 0.09/최대 2)와
`maskPathHard`(평균 0.06/최대 57 — 사유 「곡선 윤곽 1px 줄이 0.1px 어긋납니다」)를 넣었다.

**남은 선택지:** 윤곽 0.1px 을 없애려면 미리보기가 SVG 데이터 URL 을 `<img>` 로 디코딩해 그리면 된다
(렌더러와 **완전히 같은** 래스터라이저). 대가는 비동기라 마스크를 바꾼 첫 프레임이 한 박자 늦는 것.
